# pi-model v0.2 设计蓝图

> 状态：设计稿（2026-10-17），基线为已可用的 v0.1。
> 一句话：**多站 + 多 Key 可管理、模型元数据可信、pi 内秒切、任意来源批量接入**；
> 仍然零依赖、只写 pi 原生配置、写前备份、跨平台可验证。

---

## 1. 为什么做 v0.2

v0.1 已经解决了"从 0 到 1"：`pmh quick <URL> <Key>` 接入、`/switch` 切换、元数据自动对齐、
写前备份、三套离线测试。真实使用后暴露了四类短板，正好对应本次要做的四件事：

| 短板 | v0.1 现状 | v0.2 目标 |
|---|---|---|
| 多站/多 Key | 每个站一个 provider，只能靠命名区分；没有分组、收藏、最近使用；换 Key 要手写 auth.json | 注册表 + 分组/标签 + 收藏 + MRU + Key 别名 |
| 元数据准确性 | 只读 pi 官方目录，匹配不上就启发式；中转站 `/models` 自带的上下文/推理/价格被丢弃 | 优先采信中转站自己的元数据，再做合理性校验；价格支持倍率 |
| 切换体验 | `/switch [关键词]`；没有按组/收藏/最近过滤；切完没有状态反馈 | 过滤语法 + 收藏/MRU 排序 + 状态栏 + 可选站点 widget |
| 接入效率 | 一次只能 URL+Key 单条；剪贴板只认第一组 | 批量导入、订阅/分享链接、扫描 Claude Code / Codex 配置 |

### 1.1 外部调研结论（2026-10）

现有资料（`docs/资料/03-同类项目与生态.md`）写于本项目 v0.1 完成时，之后生态有新变化：

| 项目 | 形态 | 值得借鉴 | 我们的差异 |
|---|---|---|---|
| [n0rt6/pi-relay-switch](https://github.com/n0rt6/pi-relay-switch) | 纯 pi 扩展，自建 `relays.json`，动态注册 provider | 从 `/models` 读权威元数据；`compat.supportsReasoningEffort` + `thinkingLevelMap` 真正打通思考档位；常驻 widget；自动迁移旧 provider | 我们坚持写 pi 原生 `models.json`，配置可被 pi 直接读取/手改；CLI 负责批量接入与运维 |
| [OldSuns/pi-switch](https://github.com/OldSuns/pi-switch) | 终端 TUI，本地 provider 库 + 按需同步 | "库"与"pi 配置"分离；按需同步，避免频繁改配置 | 我们用轻量注册表而不是全屏 TUI；不引入框架 |
| [cc-switch](https://github.com/farion1231/cc-switch) v3.20+ | 桌面 GUI，已原生支持 Pi | 多供应商管理的心智模型；一键切换 | 不做 GUI，终端优先；不重复造面板 |
| [Wing900/Pi-switch](https://github.com/Wing900/Pi-switch) | Go + Wails GUI | provider/模型可视化 | 同上 |

结论：**不追 GUI / TUI 的壳，专注"配置正确 + 元数据可信 + 切换快 + 批量接入"**，
并把扩展保持为单文件、可单独拷走。

### 1.2 与现有 v0.1 的关系

- 所有 v0.1 命令、参数、退出码、配置写入位置保持不变。
- 新增能力默认向后兼容：没有注册表时，从 `models.json` / `auth.json` 自动回填。
- 现有 `quick-switch.js` 仍可单独使用；v0.2 只是增强，不依赖 CLI 进程常驻。

## 2. 目标与非目标

### 2.1 目标

1. **一个站一条记录**：URL、协议、分组、标签、Key 别名、收藏、最近使用都在一个地方。
2. **元数据可信**：能从中转站 `/models` 拿到的字段优先用；拿不到才降级到 pi 官方目录/启发式。
3. **秒切**：pi 内 `/switch` 支持 `@组`、收藏、最近、能力过滤；切完状态栏可见。
4. **批量接入**：剪贴板、文件、订阅链接、Claude Code / Codex 配置，一次导入多个站。
5. **不破坏现状**：只写 pi 原生字段；写前备份；密钥只在 `auth.json`；输出一律打码。

### 2.2 非目标（仍然不做）

| 不做 | 原因 |
|---|---|
| 不做网关/转发/负载均衡 | NewAPI、one-api、LiteLLM 的职责 |
| 不做桌面/Web GUI | 已有 cc-switch、Pi-switch、pi-web-switch |
| 不做用量统计/余额查询 | 数据在中转站侧，本地算不准 |
| 不修改 pi 官方文件 | 只写 agent 目录下的配置 |
| 不内置站点白名单 | 任何 OpenAI/Anthropic/Responses 兼容端点都能接 |
| 不做账号注册/激活码/自动注册 | 合规与账号安全风险 |

## 3. 用户旅程

### 3.1 批量接入（目标 ≤ 60 秒）

```text
pmh import                      # 从剪贴板读一段内容，自动识别格式
pmh import ./relays.json        # 从文件
pmh import https://x/subscribe  # 订阅链接（自动 base64 解码）
pmh import --from claude        # 扫描 Claude Code 配置
pmh import --from codex         # 扫描 Codex 配置
pmh scan                        # 只列出发现项（Key 打码），不写
```

统一流程：解析 → 去重 → 预览表格 → 确认 → 逐个拉模型列表/写配置 → 建注册表 → 可选挑默认模型。
`--dry-run` 只预览；`--yes` 跳过确认；`--no-sync` 只登记不拉模型。

### 3.2 多站日常

```text
pmh group add code --title 写代码
pmh relay group crow5 code
pmh use @code sonnet            # 只在 code 组里找 sonnet
pmh pick --group code
pmh ls --group code
pmh fav add crow5#sonnet        # 收藏
pmh recent                      # 最近用过的模型
```

### 3.3 元数据校准

```text
pmh sync crow5 --refresh-meta       # 重新拉 /models，刷新上下文/推理/价格
pmh sync crow5 --ratio              # 尝试读 NewAPI 倍率，按倍率估算价格（opt-in）
pmh meta crow5 --verbose            # 看每个模型的元数据来源与上游差异
```

### 3.4 排障

```text
pmh doctor                          # 新增：注册表/Key 别名/元数据快照状态
pmh test crow5 --verbose
pmh meta crow5 --drift              # 只列出"配置与上游不一致"的模型
```

- `models.json` 是 pi 的唯一事实来源；注册表只是"本工具的运维元数据"，丢了可以重建。

- 扩展只读注册表 + 调 pi API；不发起网络请求，不写 `models.json`。

## 5. 数据模型

### 5.1 `pmh-relays.json`（新增，不含密钥）

路径：`~/.pi/agent/pmh-relays.json`（可用 `--agent-dir` 覆盖）。
刻意不叫 `relays.json`，避免与 `pi-relay-switch` 的同名文件冲突。

```jsonc
{
  "version": 1,
  "updatedAt": "2026-10-17T09:30:00.000Z",
  "groups": {
    "code": { "title": "写代码", "createdAt": "..." }
  },
  "relays": {
    "crow5": {
      "id": "crow5",
      "name": "Crow5",
      "root": "https://x.crow5.com",
      "baseUrl": "https://x.crow5.com/v1",
      "api": "openai-completions",
      "apiRules": [{ "pattern": "^claude", "api": "anthropic-messages" }],
      "group": "code",
      "tags": ["cheap", "claude"],
      "keyAliases": ["default", "backup"],
      "activeKey": "default",
      "favorites": ["claude-sonnet-4-5"],
      "mru": [{ "model": "claude-sonnet-4-5", "at": "2026-10-17T09:31:00.000Z" }],
      "lastModel": "claude-sonnet-4-5",
      "lastSyncedAt": "2026-10-17T09:30:00.000Z",
      "metaSources": { "claude-sonnet-4-5": "upstream" },
      "costMode": "official",
      "costMultiplier": 1,
      "source": "manual",
      "createdAt": "...",
      "updatedAt": "..."
    }
  },
  "history": [],
  "settings": { "widget": "auto" }
}
```

字段说明：

| 字段 | 用途 | 谁写 |
|---|---|---|
| `root` | 归一化后的根地址（不带 `/v1`） | add/import/sync |
| `baseUrl` / `api` / `apiRules` | 与 `models.json` 保持一致的接入参数 | add/import/sync |
| `group` | 单一分组；`null` 表示未分组 | `pmh relay group` |
| `tags` | 自由标签，用于展示与未来过滤 | add/import |
| `keyAliases` | 别名列表（只有名字，不含密钥） | key 命令 |
| `activeKey` | 当前生效的别名 | key 命令 |
| `favorites` | 收藏的模型 id | `/switch-fav`、`pmh fav` |
| `mru` | 最近使用的模型（最多 20 条） | 扩展 `model_select`、`pmh use` |
| `lastModel` | 该站最后一次使用的模型 | 同上 |
| `metaSources` | 每个模型的元数据来源 | sync/meta |
| `costMode` / `costMultiplier` | 价格策略 | add/sync |
| `history` | 被替换掉的默认模型（最多 20 条），供 `pmh use -` 回退 | `pmh use` |
| `settings.widget` | `auto` / `on` / `off` | `/switch-widget` |

**重建规则**：注册表缺失或某个 provider 不在注册表里时，从 `models.json` + `auth.json` 推导：

```text
id          = provider 名
root        = rootOf(baseUrl)
api         = provider.api
group       = null
keyAliases  = auth.json 里有该 provider 的 key ? ["default"] : []
activeKey   = "default"（如果有默认 key）
mru/last    = 空
```

注册表只在首次写入时创建；只读命令不落盘。

### 5.2 `auth.json` 的 Key 别名

pi 只认 `auth.json[<provider>]`，所以**活动 Key 必须写在这个位置**。
别名存放在同一个文件里，用 `<relay>@<alias>` 作为键；pi 不会引用它，因此安全：

```json
{
  "crow5":              { "type": "api_key", "key": "sk-active" },
  "crow5@backup":       { "type": "api_key", "key": "sk-backup" },
  "crow5@team":         { "type": "api_key", "key": "sk-team" }
}
```

- `pmh key add crow5 backup sk-xxx` → 写 `crow5@backup`
- `pmh key use crow5 backup` → 把 `crow5@backup` 复制到 `crow5`，更新 `activeKey`
- `pmh key ls crow5` → 列表（打码）
- `pmh key rm crow5 backup` → 删除别名
- `pmh key <relay> <key>` → 兼容 v0.1，直接写活动 Key

别名只允许 `[A-Za-z0-9_-]{1,32}`；`default` 保留给活动 Key。
所有密钥只存在 `auth.json`，不写日志、不进注册表、不进 `models.json`（除非用户显式 `--key-in models`）。

### 5.3 `models.json` 的写入边界

只写 pi schema 允许的字段：`name`、`baseUrl`、`api`、`apiKey`、`headers`、`compat`、
`models[]`（`id`、`name`、`api`、`baseUrl`、`reasoning`、`thinkingLevelMap`、`input`、
`contextWindow`、`maxTokens`、`cost`、`compat`、`samplingParams`、`promptCache` 等）。
`apiKey` 可以写 `$VAR` / `!command` 引用（`--key-ref` / `--key-cmd`），pi 在请求时解析；
注册表字段（group/tags/favorites/mru/metaSources）**绝不**写进 `models.json`。

模型级 `compat` 在 pi 1.3.0 schema 中确实存在（已核对 `models.schema.json`），
因此 reasoning 适配可以只落在需要它的模型上，不污染整个 provider。

### 5.4 迁移

| 场景 | 行为 |
|---|---|
| 从 v0.1 升级 | 首次运行从 `models.json` 回填注册表；不改变任何 pi 配置 |
| 手工改过 `models.json` | 每次加载时按 provider 对齐；新增 provider 自动补进注册表 |
| 注册表损坏 | `doctor` 报错；加载时退回"从 models.json 重建"，不阻塞切换 |
| 删除 provider | `pmh rm` 同时删注册表条目与回退历史；Key 仍按 `--purge-key` 决定是否删，`--purge-backups` 再清历史备份 |

## 6. 元数据

### 6.1 上游元数据适配

`fetchModels()` 除了返回 id 列表，还保留原始条目 `items[]`。`metadata.mjs` 针对常见网关形状做适配：

| 来源/形状 | 识别字段 | 映射 |
|---|---|---|
| OpenRouter | `context_length`、`architecture.input_modalities`、`pricing.prompt/completion`（美元/token）、`supported_parameters` | 上下文、模态、价格（×1e6）、推理 |
| NewAPI / one-api | `context_length`、`max_tokens`、`supports_reasoning`、`supports_vision`、`*_price_per_million` | 直接映射 |
| LiteLLM | `max_input_tokens`、`max_output_tokens`、`input_cost_per_token`、`output_cost_per_token`、`supports_vision` | 映射，价格 ×1e6 |
| Anthropic `/v1/models` | `display_name`、`created_at` | 只补显示名；能力靠官方目录/启发式 |
| 通用 | `context_window`、`max_context_length`、`max_output_tokens`、`input_modalities`、`capabilities.*` | 逐个探测 |

价格统一成"美元 / 百万 token"再写入 `cost`，避免把 per-token 与 per-million 混用。

### 6.2 合并优先级

```text
用户手工覆盖（已有条目里显式改过的字段）
        >
中转站 /models 返回且通过合理性校验的字段
        >
pi 官方模型目录（精确/归一化/模糊匹配）
        >
启发式兜底
```

落地规则：

- `pmh add`：上游 > 官方目录 > 启发式。
- `pmh sync`（默认）：保留已有条目的字段，只增删模型，**不覆盖**用户手改。
- `pmh sync --refresh-meta`：按上面的优先级重新生成，但保留 `compat`、`headers`、
  `samplingParams`、`inputLimits`、`promptCache` 这类"用户可能手写"的扩展字段。
- `pmh meta --drift`：只展示"上游与配置不一致"的字段，方便确认后刷新。

### 6.3 合理性校验

上游数据不可全信，以下情况丢弃该字段并回退：

| 字段 | 合理范围 |
|---|---|
| `contextWindow` | 1,024 – 10,000,000 |
| `maxTokens` | 1 – `contextWindow`（超出则截断到 context） |
| `cost.*` | 0 – 10,000 美元/百万 token |
| `input` | 只允许 `text` / `image`，且至少含 `text` |
| `reasoning` | 必须是布尔值 |

每个模型在 `metaSources` 里记录最终来源：`upstream` / `catalog` / `heuristic` / `ratio`。
`pmh meta --verbose` 会把"哪个字段来自哪里"打出来。

### 6.4 推理档位（thinking level）

只在**有把握**时注入，避免中转站 400：

```jsonc
{
  "reasoning": true,
  "compat": { "supportsReasoningEffort": true },
  "thinkingLevelMap": {
    "minimal": "minimal", "low": "low", "medium": "medium",
    "high": "high", "xhigh": "high", "max": "high"
  }
}
```

判定条件（全部满足）：

1. `api` 是 `openai-completions` 或 `openai-responses`；
2. 模型被判定为推理模型；
3. 上游明确声明支持 `reasoning_effort`，**或**模型 id 属于 OpenAI 推理家族
   （`gpt-5`、`o1`、`o3`、`o4`、`codex`）；
4. 用户没有用 `--no-reasoning-compat` 关闭。

对 DeepSeek / Qwen / Kimi 等"有思考但未必接受 `reasoning_effort`"的模型，
默认只设 `reasoning: true`，不注入 `supportsReasoningEffort`；需要时可手动加。

### 6.5 价格与倍率

| 模式 | 行为 |
|---|---|
| `official`（默认） | 用 pi 官方目录价；上游有价格则优先上游 |
| `scaled` | 上游/官方价 × `--cost-multiplier` |
| `ratio`（opt-in） | 调 NewAPI `/api/ratio_config`，按 `model_ratio` / `completion_ratio` / 分组倍率估算 |
| `off` | 不写 `cost` |

`ratio` 换算（one-api 系常用口径，需在输出里标注"估算"）：

```text
input  USD/M = model_ratio × 2 × group_ratio
output USD/M = model_ratio × completion_ratio × 2 × group_ratio
```

读不到倍率、字段不全、或数值不合理时**不猜**，回退到官方价或留空。

### 6.6 不变量

- 官方目录里没有、上游也没给价格的模型：**不生成价格**。
- 任何"估算"来源都必须在 `pmh meta` / `pmh ls --models` 里可见。
- 刷新元数据不改变模型 id，不删除用户手工添加的模型（除非 `--keep-missing=false` 显式要求）。

## 7. 切换

### 7.1 CLI

| 写法 | 行为 |
|---|---|
| `pmh use` | 全量选择器（收藏/MRU 优先） |
| `pmh use sonnet` | 全局关键词模糊 |
| `pmh use crow5#sonnet` | 站内模糊 |
| `pmh use @code sonnet` | 只在 code 组内模糊 |
| `pmh use @fav` | 只在收藏里选 |
| `pmh use -` | 在上一个默认模型之间来回切（注册表 `history`；失效项自动跳过） |
| `pmh current [--json] [--format 模板]` | 当前默认模型一行摘要（纯本地，不探测网络）；模板支持 `{{provider}}`、`{{model}}`、`{{group}}` 等变量 |
| `pmh pick --group code` | 选择器限定分组 |
| `pmh run @code sonnet -- <pi 参数>` | 以组内模型启动 pi |

### 7.2 pi 内扩展命令

| 命令 | 行为 |
|---|---|
| `/switch` | 统一选择器：收藏 → MRU → 中转站 → 当前 provider → 其他 |
| `/switch <关键词>` | 唯一命中直接切，多命中进选择器 |
| `/switch @code [关键词]` | 按分组过滤 |
| `/switch @fav [关键词]` | 按收藏过滤 |
| `/switch recent` | 最近使用 |
| `/switch relay <id>` | 直接切到该站的 `lastModel`（没有就用第一个模型） |
| `/switch-save` | 切完写入新会话默认 |
| `/switch-fav` | 收藏/取消收藏当前模型 |
| `/switch-widget [on\|off]` | 开关站点 widget（默认 `auto`：≥2 个站时显示） |
| `Ctrl+Shift+M` | 等同 `/switch` |

### 7.3 过滤语法

查询按空白拆词，支持：

```text
@code            分组
@fav / fav:      收藏
recent:          最近使用
reasoning / 思考  只要推理模型
image / 图片      只要图片输入
ctx:>=200k       上下文下限（k/m 后缀）
provider: crow5  限定站点
其余词            走原有 id/name/provider 打分
```

多个条件取交集；没有任何命中时回退到全量列表，避免选择器空白。

### 7.4 排序

```text
第 0 组：收藏（且匹配当前过滤）
第 1 组：MRU（最近使用，最多 20 条）
第 2 组：中转站（按注册表顺序/分组，再按 provider/model）
第 3 组：当前正在用的 provider
第 4 组：其余（内置厂商）
```

### 7.5 状态与 widget

- 状态栏：`ctx.ui.setStatus("pmh", "pmh · crow5/sonnet-4-5 · 200K · 思考 · key:default")`。
- 在 `session_start`、`model_select`、`/switch` 成功后刷新。
- widget：`ctx.ui.setWidget("pmh", lines, { placement: "aboveEditor" })`，
  每个站一行：`● crow5 [code] 12 模型 · 上次 sonnet-4-5`。
- `auto` 模式：注册表里 ≥2 个站才显示；用户显式 `on/off` 覆盖。
- widget 只在交互式 TUI 下调用；异常时静默降级，不影响切换。

### 7.6 MRU 记录

- 扩展监听 `pi.on("model_select", ...)`，覆盖 `/model`、`Ctrl+P`、`/switch` 三条路径。
- 记录 `{ provider, model, at }` 到注册表对应 relay 的 `mru`，最多 20 条。
- CLI 的 `pmh use` 也记录，保证两条通道一致。
- 写注册表用"临时文件 + rename"，**不做时间戳备份**（避免每次切换产生一堆备份）；
  用户显式修改收藏/分组时才备份。

## 8. 批量导入

### 8.1 输入源

| 来源 | 写法 | 说明 |
|---|---|---|
| 剪贴板 | `pmh import` | 默认来源；识别下面所有文本格式 |
| 文件 | `pmh import ./relays.json` | 绝对/相对路径 |
| 标准输入 | `pmh import -` | 管道/脚本 |
| URL | `pmh import https://x/subscribe` | 拉取后解析；自动 base64 解码 |
| Claude Code | `pmh import --from claude` | 读 `~/.claude/settings.json`、`settings.local.json` |
| Codex | `pmh import --from codex` | 读 `~/.codex/config.toml` |
| 全扫描 | `pmh import --from all` | 上述 + 剪贴板 |
| 只扫描 | `pmh scan [--from all]` | 只列候选，不写 |

### 8.2 支持的文本格式（识别顺序）

1. **JSON**：数组、`{relays:[...]}`、`{providers:{...}}`、pi `models.json` 形状、单对象。
2. **JSONL**：一行一个对象。
3. **简单 YAML 块**：`name/base/baseUrl/key/api` 键值块，用空行或 `---` 分隔。
4. **env 块**：`BASE_URL=...`、`API_KEY=...`，块之间空行分隔。
5. **curl**：从 `curl <url> -H "Authorization: Bearer <key>"` 提取。
6. **纯文本行**：`<url> <key>`、`<name>|<url>|<key>`、`<url>,<key>`。
7. **自定义 URI**：`pmh://import?base=...&key=...&name=...`。
8. **订阅链接内容**：base64 → 递归解析（最多 2 层）。

每项统一归一化为：

```json
{ "name": "crow5", "baseUrl": "https://x.crow5.com", "key": "sk-...", "api": "openai-completions", "group": "code" }
```

### 8.3 去重与冲突

| 情况 | 处理 |
|---|---|
| 同 `root` + 同 key | 更新名称/分组/标签，不重复建 provider |
| 同 `root` + 不同 key | 视为 Key 别名：自动命名为 `backup-2` 等，提示可用 `pmh key use` |
| 同名字、不同 root | provider 名追加 `-2`、`-3`，并在预览里标出 |
| 已存在的 provider | 默认 `--merge`（保留模型与手改字段），`--replace` 才整体覆盖 |
| 解析出 0 项 | 报错并给出支持的格式示例，不写任何文件 |

### 8.4 安全

- 预览、日志、错误信息里的 Key 一律 `maskKey()`；`--json` 输出同样打码。
- 导入前必须看到"将写入哪些 provider、哪些文件"的预览；`--yes` 才跳过。
- `--from claude/codex` 只读白名单路径，不递归扫描用户目录。
- 订阅链接只发一次 GET；不跟随跨域重定向到非 http(s)；响应体限制 1 MB。
- 导入文件里的未知字段忽略，不写进 `models.json`。

### 8.5 示例

```text
# 1) 剪贴板里两站
https://a.example.com/v1  sk-aaa...
https://b.example.com/v1  sk-bbb...

# 2) JSON
{"relays":[
  {"name":"a","baseUrl":"https://a.example.com","key":"sk-aaa","api":"openai-completions","group":"code"},
  {"name":"b","baseUrl":"https://b.example.com","key":"sk-bbb","api":"anthropic-messages"}
]}

# 3) env 块
BASE_URL=https://a.example.com/v1
API_KEY=sk-aaa
NAME=a
GROUP=code

# 4) Claude Code
{"env":{"ANTHROPIC_BASE_URL":"https://x.example.com","ANTHROPIC_AUTH_TOKEN":"sk-xxx"}}
```

## 12. 风险与限制

| 风险 | 影响 | 对策 |
|---|---|---|
| 各网关 `/models` 字段命名不统一 | 元数据仍可能缺失 | 适配器 + 合理性校验 + 来源可见；缺失就回退，不猜 |

## 16. 增量（2026-10-17）：pi 原生自定义模型能力

pi 1.3.0 本身就能接入内置目录之外的模型，只是"能"不等于"方便"。这一版把不便之处补上：

| 不便 | 现状 | 现在 |
|---|---|---|
| 内置 provider 想加模型或改元数据 | 要自己理解 `models[]` 与 `modelOverrides{}` 的区别，写错会被静默忽略 | `pmh model add` / `pmh model override` 直接给出正确形状 |
| 本机 Ollama / LM Studio / vLLM / SGLang / llama.cpp | 地址、`/v1`、占位 Key 都要手填；没有 Key 时 pi 会隐藏模型 | `pmh local <服务>` 一条命令，支持 `--port` / `--base` |
| 配置写错 | pi 报错或静默跳过，用户不知道哪一项有问题 | `pmh doctor` 校验结构、模型字段、凭据与默认模型 |
| 只想改一个模型的价格/上下文 | 要重拉整站模型或手改 JSON | `pmh model override` 只写该模型，`--dry-run` 可预览 |

### 16.1 实现边界

- `src/native.mjs` 只做纯逻辑：本机预设、内置 provider 静态索引、`models.json` 校验；不读写密钥、不发网络请求。
- 内置 provider 索引从 `<pi安装目录>/node_modules/@earendil-works/pi-ai/dist/providers/*.js` 静态解析
  （`id` / `name` / `baseUrl` / `api`），不 `import` pi-ai，避免把整棵依赖树带进 CLI。
- 内置 provider 写 `modelOverrides` 时**不写** provider 级 `baseUrl` / `api`：那会覆盖该 provider 的全部模型。
- `pmh model rm` 后若 provider 已无任何可落地内容，整条配置会删除，避免 pi 因空 provider 启动报错。
- 本机服务写占位 Key 到 `models.json`（`--key-in models`），不碰 `auth.json`；服务未启动也允许先写配置。

### 16.2 校验项

`validateModelsConfig` 覆盖：`providers` 形状、空 provider、未知字段、`baseUrl` 合法性、`api` 非空、
模型 id 缺失/重复、`contextWindow` / `maxTokens` > 0、`input` 仅 `text` / `image`、`cost` 非负、
自定义 provider 的模型必须有 `api` / `baseUrl`、`modelOverrides` 类型与未知 id、
凭据可解析性（`auth.json` / `apiKey` / `$ENV` / `!cmd`）、`settings.defaultProvider` / `defaultModel` 有效性。
内置 provider 跳过凭据告警（可能有内置 OAuth / 环境变量）。

### 16.3 测试

`tools/native-test.mjs` 覆盖预设与别名、单位解析、内置 provider 静态解析、校验器正常/异常路径、
`model add/override/rm`、内置 provider override、`pmh local` 写占位 Key 且不碰 `auth.json`、补全候选。
`npm test` 现为 12 个套件，全部通过。

## 17. 增量（2026-10-17）：按任务难度自动路由

目标：在"手动秒切"之外提供可关闭的自动档位选择，**用便宜模型跑简单活、用强模型跑难活，
同时不打断 prompt cache**。

### 17.1 为什么用虚拟模型，而不是在扩展里 `setModel`

pi 1.3.0 提供 `pi.registerVirtualModel({ provider, id, route })`。虚拟模型的选中状态只记一条
`model_change`，每次响应记录的仍是实际物理模型；而扩展里主动 `setModel()` 会在每轮都写
`model_change`，污染会话恢复与会话默认值。因此：

- provider `pmh`、id `auto`，模型名 `Auto (pmh)`；
- `route(request, ctx)` 是唯一决策点，返回 `{ model, thinkingLevel, state? }`；
- 用户手动切换仍走 `/switch`，两者互不干扰。

### 17.2 路由策略（保护缓存优先）

| `request.reason` | 行为 |
|---|---|
| `user` | 仅在自动开启且未 pin 时分类；分档结果与上一轮相同则不切换、不提示 |
| `continuation` | **原样沿用** `request.previous` 的物理模型与思考档，绝不重新分类 |
| `retry` | 失败重试最多升一档（`upgradeOnRetry`），每个任务链只升一次；升档后仍失败则复用失败模型 |
| `direct` | 非对话请求固定走 cheap（省 token），关闭自动时走 pinned/standard |

状态通过 `request.state` 在会话分支内持久化：`{ tier, escalated, why }`。它只影响同一条
会话分支，不写任何全局配置。

分类只在用户新消息时发生，工具调用续跑不会触发切换——这是缓存命中率的关键。

### 17.3 三档与阈值

- `cheap` / `standard` / `strong`，默认阈值 `cheap: 0.12`、`strong: 0.5`。
- 基线 0.15；硬信号（架构/重构/并发/底层、报错与堆栈、测试或构建失败、性能/安全、算法/协议、
  实现/设计）加权，硬信号总贡献封顶 0.6；软信号（格式化/重命名、翻译/解释、注释/文档/总结、
  单行小改）减权。
- 结构信号：多文件路径 +0.1、代码块或 10 行以上代码 +0.06、祈使句 +0.06、
  长度 ≥800 +0.05 / ≥2400 +0.11、短问题 -0.08、超短输入 -0.08、含图片 +0.05。
- 结果 clamp 到 `[0,1]`，返回 `{ tier, score, reasons, files, textLength }`，`reasons` 用于
  `/auto explain` 和切换提示，保证"为什么换模型"可见。

### 17.4 用户可控性

| 需求 | 入口 |
|---|---|
| 完全关闭 | `/auto off` 或 `pmh auto off`（关闭后固定 `standard`，不分类、不提示） |
| 临时锁定 | `/auto pin strong`，`/auto pin off` 恢复 |
| 调整阈值 | `pmh auto thresholds 0.12 0.5` |
| 预览分类 | `/auto explain <任务>` 或 `pmh auto explain <任务> --json` |
| 只装扩展 | `pmh auto install` |

配置在 `<agentDir>/extension-settings/pmh-auto.json`，原子写（tmp + rename），不含密钥；
扩展每个请求重读，CLI 与扩展共用同一份，改完通常无需 `/reload`。

### 17.5 降级与边界

- 档位未配置：按方向回退（strong → standard → cheap；cheap → standard → strong；
  standard → strong → cheap），都不可用则复用上一轮物理模型或第一个可用模型，并只提示一次。
- 目标模型无凭据：跳过该档位继续回退，不抛错。
- 拒绝把 `pmh#auto` 设成档位模型（自引用）；provider/模型不在 `models.json` 时给警告但仍写入
  （pi 可能从内置目录解析）。
- 老版本 pi 没有 `registerVirtualModel`：只注册 `/auto` 并提示升级，不影响其他扩展。

### 17.7 不改 pi 本体，随 pi 升级自动适配

**决策：不 patch pi 的 release 源码。** managed install 把代码放在
`install/releases/<version>/`，`pi update` 会整目录替换，任何改动都会丢；而且会与官方行为分叉。
因此 pmh 只使用 pi 官方支持的两种接入方式：

| 模式 | 安装动作 | 更新方式 | 适用 |
|---|---|---|---|
| pi 包（`--link`，推荐） | 往 `settings.json` 的 `packages` 追加本仓库路径 | `git pull` 后重启 pi；`pi update --all` 升级 pi | 仓库常驻本机 |
| 复制（`--copy`） | 复制 `quick-switch.js` 与 `auto-router/{index,router,compat}.mjs` 到 agent 目录 | 启动时自动同步；`pmh auto sync` 手动触发 | 仓库不常驻 |

自动检测放在扩展的 `session_start`（新增 `compat.mjs`，不依赖 `src/`）。
额外的防线：已登记为 pi 包时拒绝 `install-extension --copy`（需 `--force`）；
`installedMode` 回查 `settings.json`，避免 `pi remove` 后误报；源仓库不可用时明确告警，
保留当前可用版本，不假装“已是最新”。检测流程：

1. 读 `<agentDir>/install/current-version`；读不到时退回 `releases/` 下最新的完整安装。
2. 从该 release 的 `dist/core/extensions/types.d.ts` 字符串探测
   `registerVirtualModel`、`registerCommand`、`"session_start"`；
   `hasConfiguredAuth` 实际在 `dist/core/model-registry.d.ts`，单独读取。
   约定文件读不到时，在 `dist/core` 下按关键字扫描 `.d.ts`，pi 改布局仍能工作。
3. 与 `extension-settings/pmh-compat.json` 比较，只在版本或 API 面变化时写状态并提示；
   首次记录不打扰用户。
4. copy 模式在变化时自动同步仓库最新文件，旧文件改名为 `*.bak-<时间戳>`；
   package 模式由 pi 直接加载，只做校验。
5. API 缺失时仅降级 `/auto` 并告警，`/switch` 不受影响；整个检测包在 try/catch 里，
   **任何异常都不会阻断 pi 启动**。

配套命令：`pmh auto doctor`、`pmh auto sync`，pi 内 `/auto doctor`、`/auto sync`。
模式切换是安全可逆的：从 copy 切到 package 时，复制入口改名为 `*.disabled-<时间戳>` 而非删除；
`pmh install-extension --copy` 可切回复制模式。
